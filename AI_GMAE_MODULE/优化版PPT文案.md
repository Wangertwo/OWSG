# 优化版 PPT 文案

## 第 1 页：项目定位

# 基于 Unity 的 AI NPC 与可验证动态事件系统

## 核心问题

传统开放世界 NPC 和任务系统主要依赖预设文本、固定条件和静态触发逻辑，稳定性高，但变化有限。

单纯接入大模型虽然可以提升 NPC 对话的自然度，但如果 AI 生成内容不能被游戏系统识别、执行和验证，它仍然只停留在聊天展示层，无法真正影响玩法流程。

本项目关注的核心问题是：

> 如何让 AI 生成内容不只是“说出来”，而是能在本地规则约束下进入游戏事件系统。

## 项目目标

本项目以 Unity 开放世界中的 NPC 交互和钓鱼玩法为基础，构建一个 AI 动态事件闭环：

1. AI 生成带有地点、目标、时间和可信度的候选线索；
2. 本地系统对候选内容进行解析、校验和注册；
3. 玩家主动采信线索并进入真实玩法；
4. Unity 根据钓鱼结果验证事件真伪；
5. 公告板将结果反馈为世界信息。

## 流程主线

```text
传统固定 NPC / 固定任务
        ↓
AI 生成开放性线索
        ↓
本地规则约束与事件注册
        ↓
玩家行为执行验证
        ↓
世界反馈形成闭环
```

---

## 第 2 页：问题背景与技术路线

# 从 AI 聊天到 AI 玩法事件

## 需要解决的技术矛盾

游戏系统需要确定性，AI 生成具有不确定性。二者直接结合会带来几个问题：

| 问题 | 风险 | 本项目处理方式 |
|---|---|---|
| AI 容易自由发挥 | 生成不存在的湖区、鱼类或任务 | 注入本地世界数据，限制生成范围 |
| AI 输出是自然语言 | Unity 难以稳定解析和执行 | 后端要求结构化 JSON 输出 |
| AI 内容缺少验证 | 只能停留在剧情文本 | 接入钓鱼结果进行本地验证 |
| AI 直接改状态风险高 | 破坏游戏规则确定性 | AI 只生成候选事件，本地系统裁决 |

## 技术路线

```text
玩家提出开放性请求
        ↓
本地规则判断是否需要 AI
        ↓
C++ AI 网关注入 NPC 与世界上下文
        ↓
模型生成结构化候选事件
        ↓
事件协议校验与本地注册
        ↓
玩家通过真实玩法验证事件
        ↓
结果反馈到 UI 与世界信息面板
```

## 本页重点

项目要解决的不是“能否调用大模型”，而是 AI 生成内容如何被游戏工程系统安全接纳，并转化为可执行的玩法事件。

## 第 3 页：系统总体架构

# 面向动态事件的工程架构

## 整体流程

```text
玩家输入 / NPC 对话
        ↓
Intent Router 意图路由
        ↓
Event Policy Service 事件策略判断
        ↓
C++ AI Gateway 候选事件生成
        ↓
Event Contract Validator 事件协议校验
        ↓
Dynamic Event Registry 动态事件注册
        ↓
Gameplay Verifier 玩法验证器
        ↓
Event Result Dispatcher 结果分发
        ↓
公告板 / UI / 任务 / 经济 / 世界状态
```

## 核心分工

| 模块 | 职责 |
|---|---|
| Intent Router | 判断玩家输入属于聊天、鱼闻、采信、汇报还是查询 |
| Event Policy Service | 判断当前 NPC、世界状态和玩家状态是否允许生成事件 |
| C++ AI Gateway | 构造 prompt，调用模型，解析结构化候选事件 |
| Event Contract Validator | 校验事件字段、ID、枚举、置信度是否合法 |
| Dynamic Event Registry | 管理事件注册、发布、采信、激活、完成、失败 |
| Gameplay Verifier | 根据具体玩法结果判断事件是否成立 |
| Event Result Dispatcher | 将结果分发到公告板、UI、任务、经济和世界状态 |

## 本页重点

整套架构的核心是把 AI 输出放在“候选事件”位置，再由本地系统完成校验、注册、验证和反馈。

## 第 4 页：AI NPC 交互层

# 从自然语言输入到系统意图

## 模块定位

NPC 交互层负责把玩家自然语言输入转化为系统可识别的行为意图。

它不是简单把所有问题交给模型，而是先结合 NPC 身份、职业、能力范围和当前上下文，判断请求应该由本地规则处理，还是进入 AI 生成流程。

## 处理流程

```text
玩家靠近 NPC
        ↓
打开聊天 UI
        ↓
读取 NPC 身份、职业、能力范围
        ↓
Intent Router 判断玩家意图
        ↓
稳定问题：本地规则回答
开放问题：进入 AI 候选事件生成
状态变化：交给本地事件系统处理
```

## Intent Router 在本页中的作用

Intent Router 不负责执行具体逻辑，只负责把玩家输入路由到正确系统动作：

| 玩家输入 | 路由结果 | 处理系统 |
|---|---|---|
| 你是谁 | AskIdentity | 本地 NPC 规则 |
| 鱼价是多少 | QueryFishPrice | 本地经济系统 |
| 今天有什么鱼闻 | GenerateFishingRumor | AI 候选事件生成 |
| 我要验证这条消息 | AcceptLatestRumor | 动态事件系统 |

## 本页重点

AI NPC 的重点不是自由聊天，而是让自然语言成为游戏系统入口。

## 第 5 页：C++ AI 网关实现逻辑

# Unity 与大模型之间的语义边界层

## 为什么需要 C++ AI 网关

Unity 前端不应该直接面对大模型接口。

原因包括：模型 API Key 不应暴露在客户端；不同模型供应商协议不同；模型返回格式不稳定；HTTP 超时、错误响应和解析失败不应散落在 Unity 脚本中。

因此，C++ 后端承担的是语义边界层职责。

## 网关内部链路

```text
ChatController
  - 解析 /chat 请求
  - 校验 session_id、character_id、user_text
  - 读取 mode、npc 信息、湖区与鱼类上下文
        ↓
ChatService
  - 判断普通聊天或鱼闻模式
  - 组织语义任务
  - 处理 mock、缓存和失败结果
        ↓
PromptBuilder
  - 构造普通 NPC prompt
  - 构造鱼闻结构化 prompt
  - 注入 known_lakes 与 known_fishes
        ↓
ModelApiClient
  - 适配模型 API base URL、路径、请求体和鉴权
  - 处理 HTTP 超时、非 2xx、响应解析
        ↓
ModelOutputParser
  - 提取模型输出文本
  - 解析 reply、emotion、animation
  - 解析 rumor 结构化字段
        ↓
ChatResponse
  - 返回 Unity 可消费的稳定结构
```

## C++ AI Gateway 在架构中的作用

它对应总体架构中的候选事件生成环节，负责把“玩家问题 + NPC 身份 + 本地世界数据”组织成模型任务，再把模型返回结果转换为 Unity 可以消费的数据结构。

## 本页重点

AI 网关不是转发模型请求，而是把游戏上下文转成模型任务，再把模型输出转成游戏结构。

## 第 6 页：结构化生成与本地约束

# 让 AI 输出既有变化，又不越界

## 结构化输出协议

普通聊天只需要 NPC 表现字段：

```json
{
  "reply": "string",
  "emotion": "neutral|happy|sad|angry",
  "animation": "idle|greet|talk"
}
```

鱼闻模式需要额外返回可执行事件字段：

```json
{
  "reply": "string",
  "rumor": {
    "storyText": "string",
    "lakeId": "string",
    "targetFishId": "string",
    "timeWindow": "Any|Morning|Noon|Dusk|Night",
    "confidence": 20-95
  }
}
```

## 本地约束

| 字段 | 约束来源 | 作用 |
|---|---|---|
| lakeId | Unity 已知湖区 | 限制事件地点 |
| targetFishId | Unity 已知鱼类 | 限制事件目标 |
| timeWindow | 固定枚举 | 形成时间验证条件 |
| confidence | 数值区间 | 形成风险收益判断 |
| storyText | 模型生成 | 提供沉浸表达 |

## Event Contract Validator 在本页中的作用

事件协议校验器负责把模型输出当作不可信输入处理：

```text
字段是否存在
字段类型是否正确
湖区 ID 是否属于本地数据
鱼类 ID 是否属于本地数据
时间窗口是否属于枚举
可信度是否在合理区间
```

## 本页重点

文本负责沉浸感，字段负责可执行性；prompt 不是最终边界，代码校验才是工程边界。

## 第 7 页：AI 鱼闻动态事件系统

# 从湖边传闻到可验证玩法事件

## 核心定义

鱼闻系统不是让 AI 写一段钓鱼文案，而是把 NPC 生成的湖边传闻转化为一个有地点、有目标、有时间窗口、有可信度的候选事件。

## 闭环流程

```text
玩家询问鱼闻
        ↓
AI 生成结构化传闻
        ↓
Validator 检查字段合法性
        ↓
Dynamic Event Registry 注册鱼闻事件
        ↓
公告板发布鱼闻
        ↓
玩家主动采信
        ↓
进入钓鱼玩法验证
        ↓
Gameplay Verifier 判断真伪
        ↓
Event Result Dispatcher 反馈验真 / 失准
```

## 动态事件注册与验证

Dynamic Event Registry 负责把合法鱼闻加入事件生命周期：注册、发布、采信、激活、完成或失败。

Gameplay Verifier 不依赖 AI 判断，而是检查真实钓鱼结果：

```text
是否钓鱼成功
湖区是否匹配
鱼种是否匹配
时间窗口是否匹配
尝试次数是否达到上限
验证是否超时
```

## 核心价值

1. 鱼闻不是任务指令，而是可采信的信息线索；
2. 玩家可以根据可信度决定是否投入时间；
3. 时间窗口让事件从静态目标变成行动节奏；
4. 真实钓鱼结果让传闻具备可证伪性；
5. 验真或失准结果通过公告板形成世界反馈。

## 本页重点

鱼闻系统的可玩性来自“不确定但可验证”：模型可以提出线索，但事实必须由 Unity 本地玩法系统产生。

## 第 8 页：工程可扩展性

# 从钓鱼鱼闻扩展到通用动态事件系统

## 当前落地场景

钓鱼鱼闻具备完整的事件条件：

```text
地点：湖区
目标：鱼种
时间：时间窗口
行为：玩家钓鱼
结果：成功或失败
反馈：公告板
```

这条链路能清晰展示 AI 内容如何进入玩法系统，并通过玩家真实行为完成验证。

## 可迁移玩法

| 玩法方向 | 候选事件字段 | 验证方式 |
|---|---|---|
| 狩猎传闻 | 区域、动物、危险等级、时间 | 玩家是否在指定区域猎获目标 |
| 采集线索 | 资源点、资源类型、刷新时间、稀有度 | 玩家是否采集到指定资源 |
| 商人消息 | 商品、地区、价格波动、持续时间 | 经济系统是否触发对应价格变化 |
| 任务提示 | NPC、地点、目标条件、有效期 | 任务系统是否完成对应条件 |

## 架构复用点

```text
不同玩法复用：
Intent Router
Event Policy Service
AI Candidate Event Generator
Event Contract Validator
Dynamic Event Registry
Event Result Dispatcher

不同玩法只需替换：
Gameplay Verifier
```

## 本页重点

当前鱼闻不是孤立功能，而是动态事件架构在钓鱼玩法中的落地。后续扩展时，变化的是事件字段和验证器，不变的是事件生成、校验、注册和反馈流程。

## 第 9 页：创新点与总结

# 受控生成、本地验证、玩法闭环

## 创新点一：AI 从表达层进入玩法层

AI 输出不再只是 NPC 回复，而是包含湖区、鱼种、时间窗口、可信度等可被系统执行和验证的字段。

## 创新点二：本地规则约束 AI 生成边界

AI 不能自由创造游戏世界。湖区、鱼类、时间窗口和验证规则都来自本地系统。

## 创新点三：动态事件可证伪

鱼闻可能是真，也可能失准。最终结果不由 AI 判断，而由玩家真实钓鱼行为和本地规则共同决定。

## 创新点四：信息驱动探索

玩家根据鱼闻决定去哪里、什么时候去、是否投入时间验证，使 AI 输出成为探索动机和策略资源。

## 创新点五：架构具备扩展性

当前鱼闻系统可以迁移到狩猎、采集、交易、任务提示等更多玩法，只需要扩展事件字段和对应玩法验证器。

## 最终总结

本项目通过 C++ AI 网关将大模型输出约束为结构化候选事件，再由 Unity 本地系统完成事件注册、玩家采信、真实玩法验证和公告板反馈，形成了一个受本地规则约束、可执行、可证伪、可扩展的 AI 动态事件闭环。
