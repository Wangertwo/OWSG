# C++ 后端 AI 网关模块在项目中的职责

## 一、核心判断

C++ 后端里的 AI 网关模块，在这个项目中不应该被理解为“转发大模型 API 的代理层”，而应该被理解为：

> Unity 游戏系统与外部大模型之间的语义边界层。

它的职责不是替 Unity 决定游戏结果，而是把 Unity 前端传来的游戏上下文转换成模型可理解的提示词，再把模型返回的不稳定文本转换成 Unity 可消费的稳定结构。

更准确地说，AI 网关承担四个核心角色：

1. 接口边界；
2. 模型适配；
3. 结构化约束；
4. 失败隔离。

---

## 二、第一职责：作为 Unity 与模型服务之间的接口边界

Unity 前端不应该直接调用大模型 API。

原因很直接：Unity 是游戏运行层，负责玩家交互、角色状态、钓鱼、任务、经济和 UI；模型调用涉及 API Key、网络超时、不同供应商协议、错误响应和输出解析，这些都不应该散落在 Unity 脚本里。

C++ 网关在工程上承担了一个清晰边界：

> Unity 只需要知道“我向 `/chat` 发请求”，不需要关心底层调用 DeepSeek、OpenAI Responses API 还是 Chat Completions API。

因此可以把 AI 网关定义为：

> AI 网关是游戏客户端和大模型服务之间的接口隔离层，它把模型服务的不确定性封装在后端，使 Unity 前端只面对稳定的游戏接口。

---

## 三、第二职责：接收并校验游戏侧请求

AI 网关首先不是生成内容，而是做请求边界治理。

它需要处理：

1. 请求体是否为合法 JSON；
2. 是否包含 `session_id`；
3. 是否包含 `character_id`；
4. 是否包含 `user_text` 或 `user_query`；
5. `mode`、`chat_mode` 是否可读取；
6. `npc_name`、`npc_role`、`language` 是否可读取；
7. `known_lakes` 是否为合法湖区列表；
8. `known_fishes` 是否为合法鱼类列表；
9. 玩家输入是否为空；
10. 玩家输入是否超过长度限制。

这一步的职责很重要：它保证进入 AI 服务层的不是任意前端输入，而是经过基本校验的游戏请求。

答辩时可以强调：

> 网关不是等到模型返回后才处理风险，而是在请求入口就先建立输入边界。

---

## 四、第三职责：根据游戏模式选择不同语义任务

AI 网关不是只有一种聊天模式。

它需要根据请求中的业务模式决定使用哪一种语义任务。

普通聊天模式的目标是生成：

1. NPC 回复；
2. 情绪标签；
3. 动画建议。

钓鱼渔闻模式的目标是生成：

1. NPC 回复；
2. 情绪标签；
3. 动画建议；
4. 可进入游戏系统的结构化传闻。

这说明后端不是简单把玩家文本转发给模型，而是在做游戏语义任务分发。

这一点在答辩中非常关键：

> AI 网关根据游戏场景选择不同模型任务，使模型调用从“通用对话”变成“面向玩法的语义生成”。

---

## 五、第四职责：构造受控 prompt，把本地世界数据注入模型

真正体现“AI 与游戏融合”的地方，不是调用模型，而是网关如何组织 prompt。

渔闻模式下，后端要求模型返回严格 JSON，字段包括：

1. `reply`；
2. `emotion`；
3. `animation`；
4. `rumor`。

其中 `rumor` 必须包含：

1. `storyText`；
2. `lakeId`；
3. `targetFishId`；
4. `timeWindow`；
5. `confidence`。

更关键的是，prompt 应明确要求：

1. `lakeId` 必须从 `known_lakes` 中选择；
2. `targetFishId` 必须从 `known_fishes` 中选择；
3. `timeWindow` 必须属于允许枚举；
4. `confidence` 必须处于合理区间；
5. 不允许创造未知 ID。

后端还应把以下上下文组装进用户 prompt：

1. `session_id`；
2. `character_id`；
3. `npc_name`；
4. `npc_role`；
5. `language`；
6. `user_query`；
7. `known_lakes`；
8. `known_fishes`。

所以网关的职责不是“让模型自由发挥”，而是：

> 把 Unity 本地世界数据变成模型生成边界。

答辩中可以这样说：

> AI 网关通过 prompt 把游戏世界数据前置给模型，使模型只能在本地定义的湖区和鱼类集合内生成事件线索。

---

## 六、第五职责：适配不同模型供应商协议

AI 网关还应承担模型供应商适配职责。

如果 Unity 直接接入模型 API，一旦模型供应商变化，Unity 侧就要修改请求格式、响应解析、错误处理方式。

更合理的做法是由后端统一处理：

1. 模型 API base URL；
2. 模型名称；
3. 请求路径；
4. 请求体格式；
5. Authorization header；
6. timeout；
7. HTTP 错误；
8. 响应 JSON 结构；
9. 输出文本提取。

例如不同模型 API 的返回可能是：

1. `output_text`；
2. `output.content.text`；
3. `choices[0].message.content`。

AI 网关需要把这些不同格式统一提取为一段模型输出文本，再交给后续 parser。

这一职责可以表述为：

> AI 网关是模型供应商适配层，负责屏蔽外部 API 协议差异，保证游戏侧接口稳定。

---

## 七、第六职责：把模型输出从文本解析成游戏结构

模型返回的是文本，但 Unity 需要的是结构。

因此 AI 网关要承担结构化转换器的职责。

普通聊天输出应被解析成：

1. `reply`；
2. `emotion`；
3. `animation`。

钓鱼渔闻输出应进一步解析成：

1. `storyText`；
2. `lakeId`；
3. `targetFishId`；
4. `timeWindow`；
5. `confidence`。

这一步非常关键。

如果模型输出只是自然语言文本，Unity 前端只能展示它；如果模型输出被解析成结构化字段，Unity 才能把它注册为事件、显示到公告板、等待玩家采信，并在后续钓鱼结果中验证。

所以 AI 网关区别于普通 HTTP 代理的地方就在于：

> 它把不稳定的自然语言输出转化成游戏系统可消费的结构化响应。

---

## 八、第七职责：错误隔离与降级

AI 服务一定会失败。

可能失败在：

1. API Key 缺失；
2. 网络请求失败；
3. HTTP 非 2xx；
4. 响应不是 JSON；
5. 无法提取模型输出；
6. 模型输出解析失败；
7. 模型没有按要求返回结构化字段。

AI 网关应该把这些失败转化为可识别的错误码，而不是让 Unity 前端面对混乱的模型响应。

在渔闻模式下，如果模型请求失败或解析失败，可以统一映射为类似：

```text
RUMOR_GENERATION_FAILED
```

这样 Unity 前端就可以稳定处理失败，例如提示玩家“渔闻暂时不可用”，而不是让游戏主流程崩溃。

因此可以说：

> AI 网关把外部模型的不稳定性封装成可识别的错误码，使游戏前端可以以可控方式处理失败。

---

## 九、第八职责：控制成本和重复生成

AI 网关还可以承担短期缓存职责。

例如对同一个 NPC、同一个玩家问题、同一天内的渔闻结果进行缓存。

这样做有三个价值：

1. 避免同一个 NPC 对同一个问题频繁生成不同答案；
2. 降低模型调用成本；
3. 提高短时间内世界信息的一致性。

这可以称为：

> 短期语义一致性缓存。

在 AI 游戏系统中，这个职责很重要。因为同一个 NPC 如果一分钟内对同一件事给出完全不同的说法，会破坏玩家对世界状态的信任。

---

## 十、AI 网关不应该承担什么职责

为了讲清职责边界，还要说明它不做什么。

AI 网关不应该：

1. 决定玩家是否真的钓到鱼；
2. 直接修改玩家背包；
3. 直接修改金币；
4. 直接修改任务完成状态；
5. 判断渔闻验证成功或失败；
6. 持久化完整世界状态；
7. 直接控制游戏经济系统；
8. 直接控制任务结算。

这些都应该留给 Unity 本地玩法系统。

AI 网关的输出应该是候选语义和结构化建议，而不是最终游戏事实。

这个边界非常重要，因为它能防止答辩老师质疑：

> 你是不是把游戏逻辑都交给大模型了？

正确回答是：

> 没有。大模型只生成受约束的候选语义内容，最终游戏状态仍由 Unity 本地规则系统决定。

---

## 十一、最适合答辩的定义

可以把 C++ AI 网关定义为：

> C++ AI 网关是 Unity 前端与外部大模型之间的语义中间层。它负责接收并校验游戏请求，根据普通聊天或渔闻事件选择不同 prompt，将 NPC 身份、玩家问题、湖区和鱼类等本地上下文注入模型请求；同时适配不同模型 API，解析模型输出，并将不稳定的自然语言结果转换为 Unity 可消费的结构化响应。它不直接决定游戏状态，而是为 Unity 本地规则系统提供受约束的候选语义内容。

这段话适合直接放进答辩稿或 PPT 备注。

## 十二、AI 网关架构图

```text
Unity 前端
  ↓
/chat 请求
  ↓
ChatController
  - JSON 解析
  - 必填字段校验
  - 湖区/鱼类列表读取
  ↓
ChatService
  - 普通聊天 / 渔闻模式判断
  - mock mode
  - 渔闻缓存
  ↓
PromptBuilder
  - 普通 NPC prompt
  - 渔闻结构化 prompt
  - 模型请求 payload
  ↓
ModelApiClient
  - API Key 检查
  - 请求路径适配
  - HTTP 调用
  - 响应文本提取
  ↓
ModelOutputParser
  - JSON 提取
  - reply/emotion/animation 解析
  - rumor 字段解析与兜底
  ↓
统一 ChatResponse
  ↓
Unity 本地规则系统
  - NPC 表现
  - 渔闻注册
  - 钓鱼验证
  - 公告板反馈
```

这张图表达的重点是：

> AI 网关只到“结构化响应”为止，后面的事件注册和玩法验证仍由 Unity 完成。

## 十三、对当前项目的评价

当前 AI 网关设计符合毕设目标。

它已经完成了几个关键工程动作：

1. 把模型调用从 Unity 中隔离出来；
2. 把普通聊天和渔闻生成分成不同语义任务；
3. 把模型输出解析为固定结构；
4. 对模型失败进行错误码封装；
5. 为 Unity 前端提供统一接口；
6. 保留 Unity 本地规则对游戏状态的最终裁决权。

如果后续继续优化，优先考虑两个方向：

## 1. 增加更显式的 validator 层

当前 prompt 已经约束模型输出，但更工程化的做法是增加代码级 schema 校验。

也就是说，不仅要求模型“应该这样输出”，还要用代码确认：

1. 字段是否存在；
2. 类型是否正确；
3. ID 是否在本地列表中；
4. 枚举是否合法；
5. 数值是否在区间内。

这可以把 prompt 约束升级为真正的工程边界。

## 2. 把不同 AI 任务抽象成 task handler

随着模式增加，`ChatService` 容易变胖。

可以把不同 AI 任务抽象成独立 handler，例如：

1. `DefaultChatHandler`；
2. `FishingRumorHandler`；
3. `HuntingReportHandler`；
4. `MarketNewsHandler`；
5. `QuestHintHandler`。

每个 handler 负责自己的 prompt、模型调用前后处理和输出解析。

这样 AI 网关会更像一个可扩展的“游戏语义服务层”。

---

## 十四、最终总结

C++ 后端 AI 网关在项目中的职责可以总结为一句话：

> 它不是简单代理大模型，而是游戏系统与大模型之间的语义边界、协议适配层和结构化转换层。

它向上面对 Unity，提供稳定的 `/chat` 游戏接口；向下面对大模型，处理 prompt、供应商协议、HTTP 请求、输出解析和错误隔离。

它不直接决定游戏事实，而是把模型生成内容收束成 Unity 本地规则可以理解、可以检查、可以采纳或拒绝的结构化候选内容。
